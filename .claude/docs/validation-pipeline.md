# Validation Pipeline — Pre-commit vs CI

Pre-commit and CI do not run the same hook set. Things that pass locally can still fail CI, and vice versa. Read this before wiring, judging, or debugging any validator.

## The validator test suite is a hard gate

CI runs `python -m pytest` on every PR touching `tools/` (the `unit` entry of the `checks` matrix in `tools-validation.yml`, reported as "report_lib + validator unit tests"; testpaths in `pyproject.toml` cover all six test dirs). It must be green permanently — do not introduce regressions into the testing schema. A validator's behavior and its regression tests are one change: when a `*_test.py` in `tools/validation/tests/` (or the other test dirs) breaks because a validator changed, update the test to the new correct behavior in the same commit. If the test reflects the correct invariant and the validator regressed, fix the validator instead. Never delete or weaken a regression test to make it pass; the suite is the acceptance gate for validator wiring, and a red `pytest` blocks the PR regardless of how clean the validators themselves run. Run `python -m pytest` locally before merging any `tools/` change.

## When the coding pipeline runs

`coding-pipeline.yml` triggers on `pull_request` (`opened`, `synchronize`, `reopened`, `ready_for_review`, targeting `main`, content-path filtered). Two extra entry points cover open PRs that get no pushes:

- `workflow_dispatch` (inputs `pr_number`, `base_sha`) — manual re-run for an open PR, keyed on the PR's head branch as `ref`. The PR context is rebuilt from the inputs: `PR_NUMBER`/`HEAD_SHA`/`BASE_SHA` are `inputs.X || github.event.pull_request.X` everywhere they are used (workspace cache key, manifest, report). `detect-changes` skips `dorny/paths-filter` on dispatch (no checkout, no base ref) and treats every group as changed except `style` — the style job is diff-scoped, and a dispatch has no diff.
- `nightly-pr-validation.yml` — cron (06:00 UTC) + manual dispatch. Lists open PRs targeting `main` and dispatches `coding-pipeline.yml` per PR, so validation tracks the merge ref after main advances. `base_sha` is main's live head, resolved once per sweep: it is the only component of the workspace cache key that moves when main does, and cache keys are immutable, so a stale value would make `cache/save` a no-op and replay the previous run's tree. Fork PRs are skipped (dispatch refs must live in this repo); they still validate on every push. Two more classes are warned about and skipped rather than dispatched: a PR with no `refs/pull/N/merge` (it conflicts with main, and the pipeline checks that ref out) and a PR whose head branch predates the `workflow_dispatch` trigger (a dispatch runs the workflow file as it exists on `--ref`, so those branches need a rebase first).

A report comment is only created when a run has findings (#2702). A clean run never opens one, and what it does with an existing one depends on scope:

- **full** (dispatch only, every validator ran and passed): deletes the comment.
- **partial** (per-PR, only the changed groups' validators ran): rewrites the comment in place so it stops reporting an older commit, and leaves the PR uncommented if there was never a comment. It cannot delete, because a validator that did not run this time may still have live findings from an earlier push.

Partial reports label themselves in the verdict banner and metadata strip. Scope is computed in the `validation-report` job and passed as `--validation-scope`.

## The split

- Most content validators run **CI-only**: the `validate-core` / `validate-targeted` matrices in `.github/workflows/coding-pipeline.yml` are the gate. Their old `stages: [manual]` pre-commit hooks were removed (almost nobody ran them). On `git commit` only the fast subset runs — the `md-validate-content` dispatcher (`tools/precommit_validate.py`, which fans the commit-stage validators out in parallel), plus `validate_defines.py`. Common scripting-mistake rules run once through `validate_common_mistakes.py` in that dispatcher and the CI validator matrix. To run a CI-only validator locally: `python3 tools/validation/validate_<topic>.py --staged --no-color` (drop `--staged` for a full-repo scan).
- Everything that fans out draws on one CPU ceiling: `cpu_budget()` in `tools/shared_utils.py` hands out 75% of the cores and leaves the rest to whoever is using the machine. `run_all_validators.py` caps how many validators run at once and passes each `--workers`; `precommit_validate.py` splits the same budget across its fan-out (it used to floor inner workers at 2, so fan-out times pools could reach twice the core count); `BaseValidator` clamps whatever `--workers` it is given. CI runners get every core, and `MD_MAX_WORKERS=N` overrides both. The unbounded suite fan-out that this replaced was measurably faster — the suite is largely I/O-bound — so a run that needs the old speed sets `MD_MAX_WORKERS`.
- `validate_ai_equipment.py` runs without `--strict` locally (coverage gaps would block all commits) but **with** `--strict` on CI. Equipment-coverage gaps that are tolerated locally will fail PR validation.
- `fix_loc_yaml.py` is pre-commit-only. `validate_localization_encoding.py` and `validate_mod_encoding.py` also run in the coding pipeline, so web-UI edits and contributors with hooks disabled cannot bypass the encoding checks. (The old `check_braces.py` hook was absorbed into `tools/validation/validate_style.py`.)
- `validate_defines.py` runs on pre-commit against the live install and on CI against the committed `tools/validation/vanilla_defines.txt` manifest. Regenerate it (and every other vanilla-derived file) with `refresh_vanilla_data.py` after a HOI4 version bump (see [Refreshing vanilla-derived data](#refreshing-vanilla-derived-data)).
- `validate_ideas.py` is wired into both pre-commit (`--staged --strict`) and CI (`--strict`). Undefined idea references gate; the missing-icon audit is WARNING-only and always on, with no flag to disable it. It reports three distinct failures: the sprite is undefined, it exists only under a different case (a Linux-only bug — the message names the sprite that does exist), or it resolves to placeholder art (`WIP_idea.dds` and friends, listed in `_PLACEHOLDER_TEXTURES`). The placeholder rule is what keeps the audit honest: pointing an artless idea at the WIP box no longer clears the finding, and a mod placeholder that shadows a vanilla sprite name still reports, because the mod definition is the one that loads. Backlog: ~61 findings, all placeholder art awaiting real icons. CI resolves vanilla sprites from `tools/validation/vanilla_sprites.txt`.
- `validate_mios.py` runs in both pre-commit (`--staged --strict`) and CI (`--strict`): org-id format, `allowed = { original_tag = TAG }`, initial-trait naming, trait-grid x ≤ 9, non-empty `on_complete`. The org-id, `allowed`, and `on_complete` checks gate; trait naming and x-bounds are WARNING-severity — that backlog surfaces in reports without gating. `generic_`/`GENERIC_` shared orgs are exempt, as are `generic_`-named initial traits (they reference shared traits in `MD_generic_organization.txt`). Negative x is the mod's standard organic-layout first column, so only the upper bound is a finding.
- `validate_mios.py` also carries the **MIO localisation** checks (#2730). `header-text-not-tokenized` (ERROR) fires on a `tree_header_text` whose `text` is a literal quoted string — the engine prints it verbatim, so it never reaches the loc pipeline and cannot be translated. `header-text-loc-missing` (ERROR) fires on a header token with no English key, which renders the raw token as a column header. Both gate: the 118-literal + 4-orphan-key backlog was cleared in the same change, so they are clean on main. `trait-loc-missing` (ERROR) applies the same test to `trait` / `initial_trait` names and gates: its 31-item backlog (nameless FRA traits, dead key references, unlocalised generic keys) was cleared. A staged English-localisation change scans every MIO, so deleting a key cannot evade the check. Key resolution mirrors the engine: `TAG_<key>` wins if it exists, else the bare key; shared orgs have no owner tag, so only the bare key is tried.
- `validate_mios.py` also carries the **dead equipment_bonus** checks (#3044). An `equipment_bonus` value is a percentage of the equipment's declared base stat, so a bonus naming a stat the target equipment never declares — or declares as `0` — multiplies zero and does nothing. `mio-bonus-no-base-stat` fires when no equipment in scope declares a base (the issue's case: MANPADS carry no `max_organisation`, yet `GENERIC_krepost_state_defense_bureau_proximity_fuse` grants them +10% of it as its only bonus, so the whole trait is a no-op). `mio-bonus-partial-base-stat` fires when only some of the scope declares it, which is the half-wasted `limit_to_equipment_type = { AA_Equipment cnc_equipment_type }` shape. It is **not** raised inside an `initial_trait`: an org has exactly one, it cannot be split, and a `limit_to_equipment_type` narrowing it would restrict its `production_bonus` too, so partial coverage there is unfixable by design — a wholly dead stat in an `initial_trait` is still reported. `mio-equipment-type-unknown` fires on a token in `equipment_type` / `limit_to_equipment_type` / a nested bonus key that resolves to no equipment, and suppresses the bonus check for that block — a partial scope would report every stat the missing equipment supplies as dead. `mio-bonus-no-base-stat` and `mio-bonus-partial-base-stat` are **ERROR** and gate at commit stage as well as CI: both backlogs were cleared (782 and 293 respectively), so they are clean on main. `mio-equipment-type-unknown` stays **WARNING** with a 22-item backlog.
  - Scope for the flat `organizations/` form is the trait's own `limit_to_equipment_type`, else the org's `equipment_type`, else the `equipment_type` of the org named by `include` (one org, `HOL_gkn_aerospace_manufacturer`, needs that hop). The nested `equipment_bonus = { ARCHETYPE = { ... } }` form in `policies/` and `common/country_leader/defense_company_traits.txt` keys each block by its own archetype, so it needs no resolution.
  - `NON_STAT_BONUS_KEYS` excludes the per-archetype production keys (`production_cost_factor` and friends) that legitimately sit inside a nested `equipment_bonus` — they scale production, not a stat, so they have no base to be dead against. Without that exclusion `policies/` alone reports 71 false positives. `ZERO_BASE_EXEMPT_STATS` is the escape hatch for stats the engine gives a non-zero default; it is **empty** on purpose, since an entry silences a real finding. The open candidates are the naval `*_factor` keys (`naval_light_gun_hit_chance_factor`, `naval_heavy_gun_hit_chance_factor`, `naval_torpedo_damage_reduction_factor`, `naval_weather_penalty_factor`), which appear in `modifiers_documentation.md` as unit modifiers but in no MD equipment file — confirm in game before exempting.
  - The stat index is `tools/validation/equipment_stats.py`, which folds five sources: `equipments = { }` entries (a variant's stats union into its `archetype`), modules **scoped to the slots a hull actually accepts** (pooling every module hands tank chassis the ships' `max_organisation`), `duplicate_archetypes` clones plus their `for_each` stats and `substitute` twin, `type` categories (`equipment_type` accepts `submarine` as well as `attack_submarine`), and the `mio_cat_*` groups in `common/equipment_groups/`. It reuses the brace-walking helpers and hull/module resolver in `equipment_module_slots.py`. A stat counts only when something assigns it a **non-zero** value: `infantry_weapons_type` declares `ap_attack = 0`, which is no better than omitting it. `common/units/equipment` and `common/units/equipment/upgrades` are `replace_path`'d, so MD's files are the whole universe and no vanilla manifest is needed.
  - MIO validation therefore now reads `policies/`, `common/country_leader/`, `common/units/equipment/` and `common/equipment_groups/` on top of `organizations/` and English loc. All four are in the pre-commit registry and the CI `mios` path filter, because dropping a base stat in an equipment file kills bonuses in files it does not touch; staging one of them re-scans every org, the same way a staged English `.yml` already does.

- `validate_decisions.py` carries an ERROR-severity `missing-decision-log` check (complete_effect with effects but no `log =` line). It gates: the ~650-decision backlog was cleared, so it is clean on main.
- `validate_decisions.py`'s random-seed check (`validate_random_seed`, #2731) covers both `random_list = { ... }` and bare `random = { chance = N ... }`, and exempts `fire_only_once = yes` decisions (their roll resolves once, so a cached seed can never surface). It is ERROR-severity and gates: the 11-decision backlog was cleared in the same change, so it is clean on main. An explicit `fixed_random_seed = yes` counts as a deliberate choice; only an absent field is a finding.
- `validate_localisation.py` carries two WARNING-only prose checks (#2704). `loc-em-dash` enforces the "no em dashes in player-facing strings" rule from `.claude/docs/localisation-rules.md` (backlog: 486); `loc-backtick-apostrophe` catches a backtick typed for an apostrophe (backlog: 15). Both scan only the quoted value of `localisation/english/**/*.yml` — non-English files are out of scope repo-wide.
- `validate_style.py` exempts `EH_` focus IDs via `_SHARED_FOCUS_PREFIXES` — the Event Horizon tree is generic (`event_horizon_generic_focus`) and `EH_` is its mod-wide domain prefix.
- The `styling-check` job feeds the validation report as two sections, **Style Check** (`validate_style.py`) and **Common Mistakes** (`check_common_mistakes.py`) (#3082). Each tool runs in its own step so a `--strict` style failure cannot stop the other, and both artifacts upload with `if: always()`. Slugs are load-bearing: the report derives a section title from the artifact directory name, so `validation-style-check-results` is what renders as "Style Check".
  - `check_common_mistakes.py` is not a `BaseValidator`, so it grew its own `--output` that writes the log plus the `<stem>.json` sidecar the report reads. Everything it reports is ERROR-severity; it has no warning tier.
  - `styling-check` is deliberately **absent from the `VALIDATION_SCOPE` expression** even though it is in the report job's `needs`. `detect-changes` forces `style=false` on `workflow_dispatch`, so the job is always skipped there, and a `== 'success'` test would pin every dispatch to `partial`. A dispatch therefore never produces these two sections.
  - The nightly baseline is full-repo while the CI style run is diff-scoped, so pre-existing findings on a touched file classify as EXISTING rather than NEW.
  - Seven of its checks resolve a name against mod data rather than judging a line in isolation, so they carry the same case-sensitivity teeth the rest of the repo does. `_check_equipment_type_defined` resolves `add_equipment_to_stockpile` / `send_equipment` / `add_equipment_production` / `add_equipment_subsidy` `type =` against `common/units/equipment/`, expanding each `duplicate_archetypes` clone across its archetype's numbered variants — the engine generates `medium_tank_destroyer_chassis_0` from `medium_tank_chassis_0`, and without that expansion the check reports ~2.3k false positives on history OOBs. `_check_equipment_bonus` reads `script_enum_equipment_bonus_type` from `common/script_enums.txt` and also requires `name`/`project`. `_check_active_decision_defined` resolves `has_active_mission` / `has_active_decision` / `has_active_timed_decision` against `common/decisions/`. `_check_modifier_ref_defined` resolves `add_opinion_modifier` against the replace_path'd `common/opinion_modifiers/` and `add_relation_modifier` against `common/modifiers/` — vanilla static modifiers load too, but every relation modifier MD names is its own, so the mod-only set is exact. The other three are structural: `_check_else_with_limit` (a `limit` as a direct child of `else`), `_check_nested_province_block` (`province = { province = <id> }`, which is not a selector), and `_check_log_nested_quote` (a `#`-comment swallowed into a `log` string, which closes the value early and leaves the rest to parse as effects). All seven are ERROR and gate; their combined 21-finding backlog was cleared in the same change.
  - The reference sets are read lazily and `lru_cache`d per worker, only once a candidate construct is in hand — `common/decisions/` alone is 7.6 MB, and eagerly loading it in every worker would cost more than the checks. Because the CI style run is diff-scoped, deleting a definition only surfaces its now-dead references on the nightly full-repo baseline, not on the PR that deletes it.
- `validate_building_guards.py` runs **CI-only**, `strict: false` (#2806). `damage_building` / `remove_building` against a building the state doesn't have spams `error.log`, and at raid/random-list scale that costs real performance. The check matches the `type =` the effect names against a guard trigger naming the **same** building: a bare count comparison in an enclosing `limit` (`if = { limit = { fuel_silo > 0 } ... }` and the same `limit` on `random_owned_state` / `every_owned_state` / `random_controlled_state` and friends, including through `meta_effect = { text = { ... } }` wrappers), `non_damaged_building_level` / `any_province_building_level` / `has_building` / `num_of_buildings` however deeply nested, a `random_list` bucket zeroed by `modifier = { factor = 0  X < N }`, or an `any_core_state`-style pre-selection. Tracking _which_ building types are known present is the point: an `if`/`limit` that gates on something else entirely (an idea, a flag) is still a finding. `trigger` / `available` / `visible` / `allowed` are not guards (a country-level `any_owned_state` check does not prove the effect's state has the building). `effect_tooltip` subtrees are skipped because they only preview effects and never execute. The previous 661-warning backlog is clear; the rule remains WARNING-severity during rollout.
- `validate_unused_textures.py` is wired into pre-commit as `stages: [manual]` only. CI cannot run it, so invoke the manual hook when a texture audit is needed.
- `validate_gfx_references.py` runs **CI-only**, `--strict`. Its unused-sprite check is opt-in behind `--report-unused`: the ~6.7k WARNING backlog buried every real finding, and the script ref scan that feeds only that check is most of the runtime, so a default run does neither. Pass `--report-unused` for a sprite audit; staged runs skip the check either way. Set `MD_GFX_HIDE_UNUSED=1` alongside it to drop just the orphan list, leaving the case and duplicate findings readable.
  - Sprites the engine builds from mod data are **resolved into the reference set** by `_resolve_engine_refs`, not filtered out of the report. That distinction matters: a resolved reference still reports the sprite as unused once its backing declaration is deleted, and still reports it as miscased when the spellings diverge. Six sources, all membership-based (#2982):
    - `GFX_<FOCUS_FILTER_X>` for every `search_filters` token in `common/national_focus/`. Vanilla's `nationalfocusview.gui` carries `GFX_FOCUS_FILTER_POLITICAL` only as the template placeholder; the engine swaps in the real name.
    - `GFX_EMI_<module>` for every entry in an `equipment_modules = { }` block. The ~360 `GFX_EMI_afv_*` sprites that survive belong to an AFV module set that no longer exists.
    - `GFX_SMI_<module>` for the same module and category names, ship-designer prefix. Same membership rule as EMI: a leftover icon for a deleted module still reports.
    - `GFX_unit_<subunit|category>_icon_{small,medium}[_white|_black]` from `sub_units` in `common/units/` and `sub_unit_categories` in `common/unit_tags/`. Map counters use the white/black frames; `_icon_small_small` and similar typos stay reportable.
    - `GFX_<TAG|graphical_culture|graphical_culture_2d>_ace_<m|f>_<n>`, plus the pool-less `GFX_ace_m_0` fallback, from `common/country_tags/` and `common/countries/`.
    - Anything a `[...]` template in a scripted-loc `localization_key` or scripted-GUI `image` can build, expanded to a regex over the defined set — this is what covers the 808 `GFX_missile_<TAG>_ID_<N>_icon` sprites built by `01_missiles_textures.txt`. A template with under four literal characters after `GFX_` is rejected: `GFX_[?topbar.GetTokenKey]` would otherwise mark the whole repo as used.
  - Two families stay true exemptions, since they are about ownership rather than resolution: equipment/tech/designer icons (`_is_engine_resolved_icon`) and any name vanilla also defines — a mod block under a vanilla name overrides vanilla's, so vanilla's own UI still resolves it (covers `GFX_MODIFIER_*`, `GFX_div_templ_*`, `GFX_EMSI_*`).
  - Case-sensitivity findings are split in two, because they are two different bugs. `sprite-ref-case` (ERROR) reports an English `£name` loc ref whose spelling matches a sprite only case-insensitively — the icon is simply gone on Linux. `unused-sprite-case` (WARNING) reports the mirror image: a sprite whose only reference is miscased, so the archive sweep leaves it alone. Non-English loc is out of scope (AGENTS.md), and a stray `£` before an accented word truncates at the accent (`£Réseau` → `£R`), which collides with short vanilla names.
  - `duplicate-sprite` (WARNING) reports a name defined more than once — engine load order decides which block wins — and `case-variant-sprite` (WARNING) reports names differing only in case. Both message whether the blocks share a texturefile: same art is a redundant split to collapse, different art is a silent override or two genuinely distinct sprites. WARNING, not ERROR: ~465 exact repeats exist on main and `--strict` gates on errors.
  - `undefined-font` (ERROR) reports a `.gui` `font = "x"` naming no `bitmapfont`. The engine logs `No font with name x` and renders that text box in its default face, so the layout drifts without anything looking broken in script. The universe is the mod's own `interface/**/*.gfx` declarations plus vanilla's — MD replaces vanilla's `core.gfx` by filename but leaves `fonts.gfx`, `load_screen_font.gfx`, `chatfonts.gfx` and the CJK variants alone, which is where `loadscreen_header` and `loadscreen_tip` come from. Vanilla names resolve from a live install, else `vanilla_fonts.txt`; with neither, the check skips rather than reporting every vanilla face. Clean on main (the one finding, `hoi_16` in `countryconstructionsview.gui`, was `hoi_16mbs`).
  - Sprite names in the generator-managed `.gfx` files come from the texture filename (`tools/gfx_entry_generator.py` builds `GFX_<stem>`), so a name fixed only in the `.gfx` is undone on the next generator run. Rename the `.dds`/`.png` and update `texturefile` instead.
- `validate_set_variables.py` runs **CI-only**, `--strict` (its unused-variable backlog was cleared). No pre-commit hook; run it directly (`python3 tools/validation/validate_set_variables.py`) for a local check.
- `validate_scripted_localisation.py` runs **CI-only**, `--strict` (its missing/unused scripted-loc backlog was cleared). No pre-commit hook; run it directly for a local check.
- `validate_modifiers.py` runs **CI-only**, `--strict` since #3228. It is not in `precommit_validate.py`'s registry, so `common/dynamic_modifiers/` edits get no local signal — run it directly before pushing. Only `redundant-enable-gate` is ERROR and gates; `unknown-modifier` and `dynamic-modifier-name-loc` stay WARNING, which is why `--strict` is safe here despite the frequency heuristic's known false positives. `redundant-enable-gate` flags a top-level `always = yes` or `original_tag` / `tag` inside a dynamic modifier's own `enable` (never one nested in `OR` / `NOT`, nor one inside `remove_trigger`) — see `common/dynamic_modifiers/README.md` for when a gate is genuinely load-bearing. `tools/standardization/strip_dynmod_tag_gates.py` clears them in bulk. There is deliberately no exemption list: add one only when a real case appears.
- `validate_file_paths.py` runs **CI-only**, `--strict`, in its own `validate-paths` job rather than either matrix. It reads path names from the git index (`git ls-files`), so it needs a checkout with `.git`; the workspace bundle the matrix jobs restore has neither `.git` nor `map/`. The job checks out with `filter: blob:none` and a sparse `tools` cone — the index already names every shipped path, so no content is fetched. `descriptor.mod` is read for `replace_path` directives, and a missing descriptor is a hard setup error: reading it as "nothing is replaced" would turn every inert case clash into a blocking one. Cross-references the committed `vanilla_paths.txt` manifest (CI has no HOI4 install); regenerate it after a game update via `refresh_vanilla_data.py`. Its within-mod case-collision check overlaps the pre-commit `check-case-conflict` hook on purpose — that hook only sees staged files on machines with hooks enabled, so web-UI edits and hook-less contributors bypass it exactly like the BOM fixers below.

- `validate_characters.py` runs in both pre-commit and CI (`--strict`, `characters` path filter) and covers **both leader trait pools** over one file walk — unit leader roles and advisor slots. They are checked together because they cross: deciding whether a trait is legal on a general or on an advisor needs both pools loaded, and each pool's traits are dead in the other's blocks. Its `trait-role-mismatch` check is ERROR and gates: a unit leader trait declares `type = land` / `navy` / `operative` (or `all`, or a `{ land navy }` list), and one from the wrong branch loads silently and never applies, so the leader ships with fewer traits than the script promises. Only the branch is compared — vanilla itself puts `type = corps_commander` traits on field marshals and `type = field_marshal` traits on corps commanders, so that split is not a finding (checking it produced 185 false positives). The `bold`-on-a-general backlog was cleared in the same change. `undefined-unit-leader-trait` is WARNING: 9 ALG/PHI references to traits nothing defines need content decisions, not a mechanical fix. `common/unit_leader` is `replace_path`'d, so the mod's files are the complete trait universe and no vanilla manifest is needed. `country_leader` blocks (the country leader's own traits, not an advisor's) draw from a third pool and are not scanned.

- `validate_scientist_traits.py` runs **CI-only**, `--strict`, on a `scientist-traits` path filter (`common/scientist_traits/**` plus `interface/**`, since the sprite index is the other half of the check). No pre-commit hook; run it directly for a local check. All three findings are WARNING-severity, so nothing gates on the 19-item missing-medal backlog. The engine resolves a trait's medal to `icon = X` when declared and to `GFX_<token>` otherwise (`common/scientist_traits/_documentation.md`), and an unresolved name draws a missing-texture box on the character panel: the traits are live, assigned across 10+ `common/characters/*.txt` files. The sprite index is built **MD-only** (`include_vanilla=False`), which is the one non-obvious part: `interface/unitleaderwindow.gfx` is the only vanilla file defining `GFX_scientist_trait_*`, and MD replaces that path wholesale, so 13 vanilla names are dead in game and the default (vanilla-inclusive) index would pass them. That distinction is what splits `shadowed-scientist-trait-icon` (vanilla ships the `.dds`, MD's copy just needs the `spriteType` re-declared, a 4-line fix) from `missing-scientist-trait-icon` (no art anywhere). `stale-scientist-trait-icon-todo` catches the reverse drift: a `#TODO: ICON` marker left on a trait whose sprite now exists.

- The **advisor-slot half of `validate_characters.py`** scans every file that can hold an `advisor = { }` block, including `add_advisor_role` in focuses and events. Each advisor slot owns a pool file in `common/country_leader/` (`01_high_command_traits.txt`, `01_army_chief_traits.txt`, `01_navy_chief_traits.txt`, `01_air_chief_traits.txt`), so a trait belongs to the pool of the file it lives in — **not** to whatever a `*_chief_*` name prefix suggests, which would misfile the eight vanilla-named air families (`air_air_superiority_*`, `air_close_air_support_*`, `air_tactical_bombing_*`, `air_strategic_bombing_*`, `air_bomber_interception_*`, `air_air_combat_training_*`, `air_pilot_training_*`, `air_force_multiplier_*`): they carry no `chief` in the name but are air chief traits. Splitting a pool means adding a file and one `SLOT_POOL_FILES` entry; renaming one away raises `advisor-pool-file-missing` (ERROR) rather than silently disabling the check. Everything outside the four pool files stays unclassified and exempt: `00_traits.txt`, `01_intelligence_agency_traits.txt`, `defense_company_traits.txt`, and the country files (`ENG_traits.txt`, `CHI_traits.txt`, …). `TAG_`-prefixed traits are exempt from the slot check wherever they live — they are written for one character and belong to no shared pool — but are still checked for being defined at all and for cross-pool misuse. `advisor-trait-slot-mismatch` is ERROR: the inherited 87-item backlog has been cleared, and a crossed assignment is a sprite-and-tier defect (chiefs scale 5/10/15%, high command 4/8/12%) that must not recur. `undefined-advisor-trait` and `unit-leader-trait-on-advisor` are ERROR and gate. The mirror category is `advisor-trait-on-unit-leader`: a `common/country_leader/` trait on a general, admiral, or operative loads silently and never applies. Both cross-pool categories live in the same validator, so one run decides them from one set of parsed pools.

## Check notes

- `validate_file_paths.py` exists because Windows resolves paths case-insensitively and Linux does not. A mod file whose path differs from a vanilla one only in case replaces it on Windows but loads beside it on Linux, so the two platforms hash different file sets and cannot play multiplayer together — the Kaiserreich #28202 failure, whose culprits were `common/ai_focuses/usa.txt` against vanilla's `USA.txt` and friends. The checksummed set is not all of the mod: the game's own `checksum_manifest.txt` limits it to `common/**/{*.txt,*.lua}`, `events/**/*.txt`, `history/**/*.txt` and `map/**/{*.txt,*.map,*.bmp,*.csv}`, which is why `gfx/` and `interface/` case fixes never move a checksum. Collisions inside a `replace_path`'d directory are WARNINGs, not errors — the vanilla directory is not loaded at all there, so nothing diverges while that `replace_path` stands. `replace_path` is not recursive, so the check matches a parent directory exactly, never as a prefix.

- `validate_variables.py` carries a **clamp-range conflict** check (WARNING, `clamp-range-conflict`). It harvests every literal `clamp_variable = { var = X min = A max = B }` and flags any `check_variable` on `X` that compares against a value outside `A..B` (dead logic — always true or always false), plus the inverse scale slip: a sub-1 value compared against a variable clamped to a wide integer range. That second half is the `taliban_strength > 0.19` shape, the same failure class as the `threat > 40` trap in `general-rules.md`. It is deliberately anchored on the clamp rather than on observed value spread — a plain "this variable is compared on two scales" heuristic fires on `treasury`, `inflation_rate_var` and every percentage display variable, which legitimately use both. Variables only ever written by `set_temp_variable` are excluded: a clamp on a scratch parameter (`pp_gain`) constrains that one invocation, not the variable, so its range is no invariant for checks elsewhere.

- `validate_variables.py` also carries an **unlocalised available flag** check (WARNING, `unlocalised-available-flag`). HOI4 renders a `has_country_flag` / `has_global_flag` line inside a player-facing `available` block from a localisation key named after the flag itself (vanilla does this for 672 of its 1680 country flags, e.g. `ARG_implemented_rural_reforms`), so an unlocalised flag shows the player the raw token as a requirement line. Findings are deduped per (flag, file). Checks wrapped in `custom_trigger_tooltip` / `custom_override_tooltip` / `hidden_trigger` are exempt because the wrapper supplies or suppresses the line, `visible` is excluded for the same reason as the untooltipped-`check_variable` check (a failing visible hides the object outright), and runtime-substituted flag names containing `@` are skipped as unresolvable statically. Backlog on main: 2 findings (both `has_global_flag`, added when the check was extended past `has_country_flag`).

- `validate_variables.py` also carries an **untooltipped available scripted-trigger** check (WARNING, `untooltipped-available-scripted-trigger`), one hop past the sibling above: a bare `<name> = yes` call in `available` that resolves to a `common/scripted_triggers/**` definition whose own body checks `has_global_flag` renders no tooltip at all — worse than the raw-token case, because nothing shows where the requirement line should be (the bug that motivated both checks: `pak_raj_border_available = yes` wrapping a `has_global_flag` stack). The scripted-trigger name index is built repeat-safe via a memoized full-repo scan (`ignore_staged=True`) with `HOI4_BUILTIN_BLOCKS` filtering out non-trigger top-level tokens. Narrowed to `has_global_flag`-only bodies: a repo-wide measurement including `has_country_flag` produced 270 pre-existing hits outside the border-war files (mostly stably-named eligibility/cooldown helpers), against ~43 for `has_global_flag` alone — still above the usual ~20-hit bar, so the check ships WARNING-only (never gates `--strict`) with the narrower pattern rather than being weakened further or dropped. Same wrapper exemptions and `visible` exclusion as the sibling checks. A wrapper around the flag _inside the scripted trigger_ also exempts the call site, because that wrapper already supplies (or hides) the requirement line. `can_do_african_union_focus` is the example: its mandate `has_global_flag` and outlook `check_variable`s sit in `custom_trigger_tooltip` blocks, so a bare `can_do_african_union_focus = yes` is not a finding.

- `validate_variables.py` also carries two **dynamic-modifier tooltip** checks, both WARNING. `variable-tooltip-missing-loc` flags a `tooltip = KEY` inside a variable effect whose key has no English loc entry — the engine renders the raw key, so the player reads `air_range_factor_tt` where the modifier line should be. It covers every non-temp variable effect (`set_`/`add_to_`/`subtract_from_`/`multiply_`/`divide_`/`clamp_variable`), is deduped per (key, file), and fires anywhere in `common/` or `events/`: a broken key is broken wherever it sits. `dynamic-modifier-tooltip-missing` is the other direction — an `add_to_variable` / `subtract_from_variable` moving a variable that backs a dynamic modifier with no `tooltip =` at all, so the modifier changes silently. The backing-variable map is built from `common/dynamic_modifiers/` at depth 1 only (depth 2 would drag `remove_trigger` / `enable` body keys in as variables), with `var:` / `global.` / `TAG.` prefixes and `^N` array indices normalised away; one variable can back several modifier keys, and the message lists every `<modifier_key>_tt` that resolves, or asks for the key to be added to `MD_dm_modifiers_l_english.yml` when none does. Unlike its sibling it is scoped to the block kinds the engine actually renders — `complete_effect`, `timeout_effect`, `remove_effect`, `completion_reward`, event `option`, MIO trait `on_complete` — which is what keeps `history/` bootstrap writes, `common/scripted_effects/` helpers (usually covered by one `custom_effect_tooltip` in the caller) and `on_actions/` out of the findings without a directory allowlist. `cancel_effect` is excluded deliberately: it fires on cancellation, not a player action. `hidden_effect` suppresses both checks at any depth, since it swallows every tooltip below it. Backlogs on main: 156 findings / 82 distinct keys, and 262 findings. Flip both to ERROR once cleared.

- `validate_events.py` carries a **date-gated scheduling** check (ERROR, `date-gated-not-scheduled`). MD fires its historical events from `common/scripted_effects/00_yearly_effects.txt` and uses the event's own `date >` check only as a guard, so an event carrying the guard with no scheduling entry is dead content: it is triggered-only, and nothing fires it. Only `date >` counts: a `date <` bound alone is an expiry guard on a chain event and says nothing about scheduling. Three exemptions: an event reachable from a scheduled ancestor in the event→event fire graph inherits that schedule; a fire from `common/national_focus/` or `common/decisions/` is a player-driven availability window with no scheduled moment to belong to; and if the scheduling file schedules nothing at all (a rename, or a scoping mistake) the check logs and skips rather than reporting all ~75 scheduled events. A fire from `common/on_actions/` is deliberately **not** exempt: a daily on_action waiting for a date is a poll, and the yearly effects are its intended home. Two on_action fire paths are modeled as schedules rather than dead content: a `random_events = { weight = ... }` pool weights its events by MTTH (the pool is the schedule), and a chance-rolled `random = { chance = N ... }` poll emulates MTTH and has no deterministic yearly slot. Both are exempt. The check ships as an **ERROR**. `event-fire-type-mismatch` separately reports a fire whose effect keyword does not match the declaration (`country_event` targeting a `news_event`, for example) and is ERROR-severity. `malformed-event-fire` catches reversed `event_country` calls and event blocks missing `=` and is ERROR-severity.

- `validate_on_actions.py` reports deterministic `date >` polling from `on_daily[_TAG]`, `on_weekly[_TAG]`, and `on_monthly[_TAG]` as `deterministic-date-poll`. Historical events belong in `00_yearly_effects.txt`; chance-rolled polls remain exempt. The check is ERROR-severity. The two Howard election placeholders and `the_new_look_rudd.1` intentionally remain weekly/monthly retries, so they are explicit exemptions.

- `validate_oob_units.py` slot-checks every `create_equipment_variant` through
  `tools/validation/equipment_module_slots.py`, resolving module-driven slot unlocks
  and `duplicate_archetypes` clones first. Ship, tank, and plane designs are all
  checked: required slots, hull `module_count_limit`, and module
  `forbid_equipment_type` / `forbid_equipment_type_exact_match` are ERROR; slot and
  category mismatches are ERROR on created variants. `validate_ai_equipment.py`
  applies the same slot rules to `target_variant` designs, with category-mismatch
  still WARNING pending the existing backlog. Both run `--strict` on CI. It also structurally checks `create_unit`
  effects: state scope, `owner`, block keys, a single-line division string
  that parses as army data (documented inner keys, quoted `name` /
  `division_template`, numeric factors, `force_equipment_variants` shape),
  zero equipment/manpower factors, and the order of a template defined in the
  same file and effect path as the `create_unit` using it. German/Danish letters
  in that string (`äöüßæøå`) are WARNING (`out-of-bounds-division`): the inner
  parser rejects them even inside quotes (Sweden `militärdistriktet`). Romance,
  Slavic, and Kurdish accents are allowed; they render in game. Schema failures
  gate. If a `create_unit` names a template that `delete_unit_template_and_units`
  removes anywhere, and this effect neither creates that template earlier nor
  sits behind a `has_template` guard, that is WARNING (`missing-template-ensure`).
  persistent.cpp reports the missing template as `Malformed token: <name>`.
  Requiring the ensure pattern on every `create_unit` is 544 findings, mostly
  legal OOB spawns, so the check is limited to names that are also deleted.
  A `<effect> = yes` call earlier in the same effect also counts when that
  scripted effect creates or guards the template, followed transitively, so the
  ensure block can be factored out instead of inlined at every call site.
  The backlog was cleared in the same change and the check is clean on main.
  It stays WARNING because the covering-template resolver is a heuristic: a
  bare `ROOT`-scope definition is taken to cover the whole effect, and a
  `has_template` guard naming a template nothing defines still passes. Its
  combined run gate covers `history/countries/`, `common/national_focus/`,
  `events/`, `common/decisions/`, `common/special_projects/`,
  `common/scripted_effects/`, `common/on_actions/`, `common/operations/`,
  `common/resistance_compliance_modifiers/`, `common/scripted_guis/`, and
  `common/ideas/` (deletions live in idea removal effects), in both the
  pre-commit registry (`tools/precommit_validate.py`) and the CI `oob` path
  filter. `config_drift_test.py` derives those routes from
  `_CREATE_UNIT_SOURCE_PATTERNS`, `_DELETE_TEMPLATE_SOURCE_PATTERNS`, and
  `_VARIANT_SOURCE_PATTERNS`, so a new directory there fails the suite until
  both are updated.

- `validate_decisions.py` carries a **missing icon** check (WARNING, `missing-decision-icon`), opt-in behind `--missing-icons` and **not** wired into CI. Resolution follows the engine and differs per site: a decision `icon = X` is accepted if `X`, `GFX_decision_X` or `GFX_X` is defined (a bare name is the dominant MD convention and is **not** a bug — see `.claude/docs/decision-reference.md`); a category `icon = X` takes the `GFX_decision_category_` prefix instead, so a sprite that only exists as `GFX_decision_X` does not satisfy it; a category `picture` is always the full sprite name. Values already starting with `GFX_` are only tried verbatim, never double-prefixed. Dynamic `icon = { key = ... trigger = ... }` blocks contribute one check per `key`, and `[...]` values are skipped as runtime-resolved. Backlog on main: 355 decision + 79 category findings with vanilla sprites in view (596 without, see `sprite_index.py` below); flip to ERROR once cleared. The same `--missing-icons` flag drives the sibling check in `validate_focus_tree.py`; `validate_ideas.py` no longer takes the flag, since its audit is always on. `validate_decisions.py` and `validate_focus_tree.py` remain manual. `run_all_validators.py` carries the flag for focus-tree only.

- `validate_decisions.py` also carries an **icon slot** check (WARNING, `decision-icon-slot-mismatch`), always on. The decision UI draws every icon at its texture's native size — the category tab's `icon` (`interface/countrydecisionview.gui:97`) and the decision row's (`:411`) both declare a position and no size — so art authored for one slot renders oversized or shrunken in the other. Sprite names cannot tell the slots apart: MD categories use both `GFX_decision_category_*` and `GFX_decisions_category_*`, and category `picture` banners carry the plain `GFX_decision_*` prefix, so the check classifies by the texture's pixel size instead (`image_size.py` reads DDS/TGA/PNG headers; `sprite_index.build_sprite_texture_index` maps sprite name to texture path). Vanilla sets the three families: decision icons cluster at 33x32, category icons at 52x40, category pictures at 114x101. Bands are keyed on the longest edge with deliberate gaps between them (decision ≤ 36, category icon 48–79, picture ≥ 80) — MD has a handful of in-between textures that read as either family, and a size landing in a gap identifies no slot and is not reported. A value resolving to no sprite is left to the missing-icon check rather than reported twice. Backlog on main: 444 findings over 69 files, mostly category-sized art on decisions. The 48 sites that had a correctly-sized sibling sprite are already swapped; what remains is bespoke art authored at the wrong size, which needs the texture resized rather than a different sprite, so this stays WARNING.

- `sprite_index.py` (shared by the event, focus, and decision icon checks) indexes the mod's `interface/*.gfx` plus a live HOI4 install when `include_vanilla=True`, and deliberately does **not** fold in the committed `tools/validation/vanilla_sprites.txt` manifest. Decision and focus icon audits still need a live install to avoid vanilla-sprite noise. `validate_ideas.py` also falls back to the manifest because its WARNING-level audit runs in CI without an install. The event-picture check passes `include_vanilla=False` regardless: MD must not rely on vanilla event pictures.

- `validate_localisation.py` carries a **typo watchlist** check (WARNING, `loc-typo-watchlist`) against `.claude/docs/typo-watchlist.md`'s catalogued misspellings. It scans prose in loc values, excluding loc keys and runtime references (`[...]`, `$...$`, and `£...`). `it's` and `civilisation` are excluded as context-dependent. The backlog is clear; flip to ERROR when warning-only rollout is complete.

## Refreshing vanilla-derived data

CI has no HOI4 install, so six checked-in files stand in for the game. `tools/validation/refresh_vanilla_data.py` rebuilds all of them from a local install (auto-detected, or set `$HOI4_PATH`):

| Target    | File                                     | Read by                                                                        |
| --------- | ---------------------------------------- | ------------------------------------------------------------------------------ |
| `defines` | `tools/validation/vanilla_defines.txt`   | `validate_defines.py`                                                          |
| `docs`    | `resources/documentation/*.md`           | `validate_modifiers.py` (verbatim copies of the game's own `documentation/`)   |
| `fonts`   | `tools/validation/vanilla_fonts.txt`     | `validate_gfx_references.py` (undefined-font check)                            |
| `gui`     | `tools/validation/vanilla_gui_files.txt` | `validate_gfx_references.py` (MD-authored vs vanilla override → ERROR/WARNING) |
| `paths`   | `tools/validation/vanilla_paths.txt`     | `validate_file_paths.py`                                                       |
| `sprites` | `tools/validation/vanilla_sprites.txt`   | `validate_gfx_references.py`                                                   |

```bash
python3 tools/validation/refresh_vanilla_data.py
python3 tools/validation/refresh_vanilla_data.py --only docs sprites
```

Run it after every HOI4 version bump and commit the diff. Stale data does not fail CI. It produces false positives instead, which is worse: a modifier Paradox added after the last refresh reads as a typo, and a sprite added in the same patch reads as an undefined reference.

The `docs` target is a straight file copy with no reformatting, so `diff -r resources/documentation "$HOI4_PATH/documentation"` is the staleness check.
